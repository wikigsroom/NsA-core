# 开发计划与验收矩阵

版本：需求基线草案 v1.1；日期：2026-11-06（UTC+08:00）。

关联文档：[需求说明书](游戏大厅二次开发需求说明书.md)、[技术方案与接口约定](技术方案与接口约定.md)。需求编号以说明书为准；本文件把它们落实为工作项、验收方法和交付条件。**所有工作项与验收案例均为计划，没有因为本文列出而自动完成。**

## 1. 交付原则

最终交付是一个能完成真实流程的产品：全新安装统一 App → 浏览真实目录 → 从服务下载 → 完成校验和安装 → 在 App 内操作游戏 → 返回大厅 → 再次启动读取存档。不能用预置在手机里的文件、静态游戏下载页、自动播放视频、跳转另一个游戏 APK，替代这条闭环。

先验证同一 APK 的多游戏运行能力，再投入完整界面和运营功能。传输层可以用自行生成的大文件、合法测试资源验证规模；这类测试不能证明游戏运行和存档已经通过。

产品验收与单款游戏优化分别计量：大厅和下载完全正确，也不能把低帧率或频繁崩溃的游戏标为本机“已验证可玩”。现有《旷野之息》仅能作为内部实验样本；其公开分发范围与正式性能证据仍是独立事项。

## 2. 阶段、输入和退出条件

| 阶段 | 必要输入 | 必须交付与验证 | 退出条件 |
| --- | --- | --- | --- |
| G0：运行架构验证 | 两款可用于相应测试范围的真实内容、各自可重现的编译 profile、参考机与测试账号/资格清单 | 唯一模块库名与注册表、bootstrap ABI、游戏独立进程、显式启动路径、退出/崩溃事件；同一 APK 执行 A→大厅→B→大厅→A，分别保存并读档 | 两个 profile 实际加载且数据不串用；原生退出不会终止大厅；模块与内容匹配有证据；声明系统上的执行代码加载与页大小范围已验证。假设失败就修正方案，不进入大规模界面铺设 |
| G1：最小真实闭环 | G0 通过、签名发行清单、可下载的两款内容、最小目录服务 | 游客大厅、搜索/详情、兼容检查、持久化单下载、受控安装、启动与返回、基础存档、最小发布工具 | 从全新安装且未预放游戏文件的手机出发，完成真实下载和双游戏切换；离线重开、重复点击、普通暂停恢复与存档重载通过。HTTPS 测试服务可以受控部署，不能在正式客户端关闭证书验证 |
| G2：可靠性与运营 | G1 闭环、正式包与 API schema、版本关系和存档兼容样本 | 网络/系统中断恢复、大文件与大量小文件、安装日志恢复、权限边界、更新/回退、后台发布审核、日志和诊断 | 首版全部 P0 功能案例通过；故障注入后不丢已提交存档、不启动半包；发布权限与撤回策略可演练；参考系统传输机制覆盖完成 |
| G3：有限范围发布候选 | G2 通过、签名保管与发行说明、已批准的内容范围、参考设备兼容记录 | 新装和升级安装包、公开/内测目录、真机长时操作、更新与恢复演练、服务监控和备份、许可资料、使用帮助 | 功能与性能门槛分别通过；对未通过游戏/设备降为实验或不开放；已知 P0 缺陷为零，服务和回滚责任人明确；形成可审阅候选，不自动视为已经对外发布 |
| G4：后续扩展 | G3 运行数据与新增游戏需求 | 按需开展 P1、云存档、更多设备、profile 数据化、内容增量交付与渠道扩展 | 新能力有独立需求、兼容测试和数据迁移；不通过改变旧字段含义破坏已发布客户端 |

G0 在当前手机上可以验证流程架构，但当前手机不必因此成为正式游戏性能参考机。若首发游戏都无法在拟支持设备达到正式可玩门槛，应调整游戏/设备范围或另立性能适配任务，不能靠调低目录文案要求掩盖结果。

## 4. 验收矩阵的使用方式

以下 58 个案例覆盖需求说明书的 90 个功能与质量编号。P0 是首版应通过的用例；P1 用例仅在该扩展进入相应版本时验收。下表是方法和预期结果，**不是已执行的测试报告**。

每次执行至少登记：案例 ID、App 版本/提交、模块/内容包/驱动版本、设备与系统、初始安装和存档状态、网络/存储条件、操作步骤、实际结果、证据位置、缺陷编号与执行时间。截图和日志隐去序列号、个人路径、签名 URL 和凭据；游戏数据及密钥不随测试记录进入 Git。

## 5. 参考设备和覆盖计划

所有设备覆盖指物理机；本项目不使用 Android 模拟器、Docker、WSL 或其他本地虚拟化环境。开发机可以运行原生 Windows 的客户端构建、服务和测试工具。

| 设备/环境组 | 需要验证什么 | 当前证据与缺口 |
| --- | --- | --- |
| 当前 Motorola edge+，Android 12 / API 31，Snapdragon 865 / Adreno 650 | 旧目标系统调度、触屏、生命周期、实验游戏运行、存读档与统一大厅额外开销 | 既有单游戏 App 已到可操作场景并写档，约 7–13 FPS；统一大厅、读档、30 分钟测试均未由此证明。GPU/驱动组合仍为实验 |
| 首发较高性能 ARM64 物理参考机 | 正式游戏性能基线、图形功能、热稳定、内存和 30 分钟场景 | 机型待 DEC-04 确定；不能直接引用上游另一台设备成绩作为本产品结果 |
| Android 14 / API 34 物理机 | UIDT 的启动、通知、系统停止、恢复与前后台限制 | 需要新增真机证据；API 31 设备无法覆盖此路径 |
| Android 15/16 物理机，候选 App 按当前目标 API 构建 | 适用的后台/前台服务规则、native 加载、权限、升级与系统回收 | 需要新增真机证据；目标 API 数值正确不等于各行为都兼容 |
| 16 KB 页 ARM64 物理机，若纳入发行范围 | ELF 与 APK 对齐、所有 native 依赖、改写程序映射、运行与退出 | 不能只检查 ZIP 对齐就宣布通过；没有对应真机时记录未覆盖，并收敛支持范围 |
| 不同 RAM/可用空间和不满足图形能力的物理机 | 启动前判定、空间预算、低内存恢复、未支持原因 | 不用虚拟内存地址预留量推导实际 RAM；不支持的组合要验证正确阻止或实验提示 |
| 手机/平板、触屏与声明支持的物理手柄 | 安全区域、字体/读屏、方向和配置变更、输入热插拔 | 每项支持声明都需证据；无需为首版承诺尚未验证的全部外设 |

同一台机器可以覆盖多个环境组，但一次结果不能跨系统、驱动或版本自动继承。每次改变核心、驱动、shader 生成链或高风险补丁，按影响范围重新验证，不要求无依据地重测所有不相关内容。

## 6. 估算、人员和关键路径

以下是**用于讨论投入的初步估算，不是排期承诺**。按复用现有运行层、固定两款已适配内容、小规模官网渠道、无交易和云存档估计。G0 结束后应根据实测改写，新增游戏适配另计。

| 工作面 | 建议角色 | 初步工作量 |
| --- | --- | --- |
| G0 架构与样本验证 | 原生工程师牵头，Android 配合 | 2–4 人周 |
| Android 大厅、任务、安装和运行协调 | Android 工程师，原生配合 | 6–10 人周 |
| 目录/下载授权/发布后台与服务运维基础 | 后端工程师 | 4–6 人周 |
| 统一内容制作、签名、构建与候选交付 | 原生/发布工程 | 3–5 人周 |
| 跨模块故障、规模、真机和版本验收 | 测试牵头，全栈修复配合 | 4–6 人周 |
| 合计 | 各工作面互斥计入一次，G0 试作成果后续复用 | 19–31 人周 |

若由 Android、原生、后端各一人，加部分时间测试/产品协作，初步可用 10–16 个日历周讨论依赖和缓冲；不能把总人周简单平分后当作准确工期。缺测试设备、内容范围未确定、G0 ABI/系统加载失败等会改变基线。

本估算不包括：新游戏逆向/补丁适配、大量标题逐一转制与设备认证、让当前《旷野之息》从 7–13 FPS 提升至正式门槛、研究《王国之泪》在当前机表现、获取内容分发范围、商店模式重构、付费交易或完整账号/云存档。以上工作不应被隐藏在“加一个大厅”的工时中。

关键路径建议为：T-01 → T-02/T-04 → T-03 完成 G0 → T-08/T-09/T-12 → T-13 完成 G1 → T-15/T-16/T-20 → T-21/T-22。界面和后台可在协议稳定后并行，但不提前假定 native 多模块已经可用。
