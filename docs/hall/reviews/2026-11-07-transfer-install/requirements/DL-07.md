### Candidate findings

#### F01 — Successful worker strands games confirmed after its one-time queue snapshot

**Severity:** Medium / P2. **Rules:** DL-07.01; AC-D05. **Confidence:** high. **State:** awaiting independent refutation.

The active worker reads candidates once at `TransferWorker.kt:L35`. Confirming B while A is transferring inserts B (`HallRepository.kt:L157`) but its schedule uses KEEP (`L166-L168`), so WorkManager discards that new work while A's work is unfinished. The loop never queries again, and if the original snapshot succeeds, `L50` returns success with B still queued. No completed-worker hook or transfer-table observer schedules a successor.

Source reproducer (not executed):

1. Confirm game A; allow worker W to pass `TransferWorker.kt:L35` with candidates=[A].
2. While A downloads (before its installation operation lock), confirm a different game B. Its row commits; its same-name KEEP request encounters running W.
3. Let A download/install successfully, with no Interrupted/error path.
4. W returns success after its original list. B remains run/queued; it has no executor. Avoid toggling network preferences, explicit resume/cellular commands, finishing a game session or recreating the process, which can supply a later schedule call.

This is ordinary multi-game queue use. Reopening a page or refreshing the catalogue does not fix it: `initialize` returns early when initialized (`HallRepository.kt:L61`), refresh does not schedule (`L92-L124`), and periodic maintenance only trims logs. If a prior candidate sets retry=true, the next attempt can pick B up; the finding is the all-success path, not every queue run.

Correction target: coordinate enqueue and drain completion so every runnable committed task is either included in a continuing drain or has a persisted successor; recheck the queue at completion with race-safe scheduling.

#### F02 — Worker's stale full-row progress write can revive a cancelled task after its replacement is queued

**Severity:** Medium / P2. **Rules:** DL-07.01, ownership aspects of DL-07.02; CON-07. **Confidence:** high for the source interleaving; Android timing acceptance unexecuted. **State:** awaiting independent refutation.

`TransferWorker.kt:L139` reads a run row, then `L140` Upserts the entire copy, including its old intent. Cancellation at `HallRepository.kt:L175` writes cancel/cancelled without a shared lock, revision or conditional update. The same-game enqueue guard immediately treats cancelled as free (`L146`). The nonunique gameId index and unrestricted Upsert do not protect against the stale worker write (`Database.kt:L9,L27`).

Source reproducer (not executed):

1. Use an established multi-chunk A download, with its stored state already downloading. Pause scheduling of the worker immediately after `L139` returns a snapshot with intent=run and before its `L140` Upsert commits.
2. In the download centre, cancel A and confirm. `transferAction(A,"cancel")` writes terminal state. Because its prior state was downloading, this branch does not immediately delete A's directory.
3. Return to the same game's detail and confirm replacement task B. This is reachable: `HallApp.kt:L111` excludes cancelled rows and `L243` offers download. `enqueue` also excludes cancelled, so B commits.
4. Resume the worker's `L140` write. It overwrites A back to intent=run/state=downloading. Both A and B are now active rows for one game, and A continues despite its cancellation.

UI action serialization does not refute this: the worker is independent of the ViewModel action mutex, and its progress write does not hold `operationLock`. Enqueue's lock only surrounds enqueue; cancel and progress mutation do not share it. Unique WorkManager work still serializes actual game transfers, so this finding does **not** assert simultaneous connections or simultaneous extraction. A and B have different transfer directories (`TransferWorker.kt:L103`), while their installations are serialized. The established consequence is loss of cancellation and duplicate same-game operations/copies; extra download/install work can follow when B is later scheduled.

The same stale-write pattern can erase a pause. Also, `enqueue` treats failed as free and retry has no ownership check (`HallRepository.kt:L146,L174`), contrary to failed ownership retention in `05-data-state.md:L61`; however, normal detail UI still projects failed as an existing task. Do not report “ordinary failed-task click always creates a duplicate” without an additional reachable command sequence.

Correction target: preserve durable intent with conditional progress/state updates, acknowledge cancellation before releasing operation ownership, and enforce the one-active-operation-per-game invariant in both the database and coordinator.

#### F03 — Queue lacks the required task-ID tie-break and exposes the reverse order without a position

**Severity:** Low / P3. **Rule:** DL-07.01; AC-D05/S05. **Confidence:** high. **State:** awaiting independent refutation.

Both execution and UI reads use only `ORDER BY created` (`Database.kt:L24-L25`), although the rule requires confirmation time then task_id. Creation time is millisecond wall-clock sampled when the record is inserted (`Database.kt:L10`), with a random UUID (`HallRepository.kt:L157`). Equal timestamps have no specified ID ordering. S05 reverses this list (`HallApp.kt:L420`) and the card displays only generic 排队等待, with no queue position (`L443-L461`); the apparent list order is newest-first while execution is oldest-first.

Source reproducer (not executed): have two queued records with equal created timestamps and IDs ordered opposite their insertion order, then inspect the query and worker order; no ORDER BY id or coordinator comparator enforces the required tie-break. For the visible mismatch, confirm B after A is already active; B is listed above A without “waiting #N” or an explanation that the list is reverse history rather than execution order.

No game data loss is established. This is a deterministic ordering and queue-explanation defect, not a concurrency finding. Correction target: persist a stable confirmation order, sort by that order and task_id, and show the effective queue position/reason.

### How the verdict was reached

This is partial because the ordinary single-worker/inline-install path provides real deduplication and serial I/O, while the finite queue drain and stale progress mutation break other required paths. It is not “absent”: unique scheduling, UI/application locks, durable intent, task-root derivation, sequential requests and installation locking were all traced to callers and callees.

The lack of a separately owned transfer lease is a source gap in the specified ownership design. WorkManager's durable named work and duplicate-runner suppression are real compensating enforcement, so absence of an app lock alone is not evidence of simultaneous production writers. No unsupported simultaneous-file-write candidate is promoted here.

### Open questions and unverified acceptance

- AC-D05's actual connection/file-handle/queue-log evidence has not been generated in this audit. All three findings are source deductions, awaiting independent code/spec refutation and later focused validation.
- Whether an Android stop/restart can overlap a blocked old HTTP call and a new worker requires a verified framework lifecycle path/device evidence. `Api.open` does not attach call cancellation, but two production archive writers were not proven. Do not equate the missing explicit lease with a reproduced collision.
- True confirmation chronology when the device wall clock changes, same-millisecond ties and queue-log observability need acceptance. F03's missing tie-break/reversed display is directly visible in source.
- Same-volume accounting for reservations owned by unrelated operations and App APK updates is broader than this game-queue audit. The positive DL-07.04 assessment covers bounded game extraction under the existing one-worker/global-operation-lock route, not all storage requirements.
- API34 UIDT absence is retained only as an adjacent DL-10 handoff. No new source edits or acceptance-status upgrades are included.
