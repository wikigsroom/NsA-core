**Verdict:** partial · confidence: high for inspected source; no dynamic acceptance claim.

Source pinned to `189169fded9cd6557b3cb146b56d8b2e5243d705`. HEAD matched before and after inspection. The working tree was initially clean. This was a read-only inspection of application/service/contracts/test source and a cached dependency's bytecode. No application tests, network, browser, ADB, phone, Docker, WSL, VM or emulator were used. Only this report and its JSON counterpart were written. The other project's phone test was not accessed.

**What this demands:** the signed manifest fixes release/object/length/SHA and signed indexes; temporary URL changes must preserve that identity. Same-object URL renewal must retain verified chunks. Changed identity must not silently repurpose an existing task.

AC-D04 requires controlled 206/200/ETag/length/416/expiry/renewal responses and final file hashes: `docs/product/开发计划与验收矩阵.md:L91`; `docs/product/data/acceptance.json:L147-L154` explicitly remains `not_run`.

## DL-06.01 — 固定对象与强 ETag 条件

> Range 请求固定 object_id、长度、摘要和强 ETag 条件；临时 URL 只是访问位置。
> — `docs/product/产品需求细则.md:L407`

**Verdict:** partial · confidence: high.

**Where enforcement lives:**

- `android/app/src/main/java/org/nsa/hall/data/HallRepository.kt:L144-L157` verifies a signed manifest against detail SHA, checks game/release, stores that manifest and signed archive length in a new `TransferRecord`. Signature/hash verification is actually performed by `android/app/src/main/java/org/nsa/hall/security/Trust.kt:L73-L86`, rather than inferred from its name.
- `HallRepository.kt:L140-L142` requests a session for the manifest's release, verified manifest SHA and requested object ID. The application does not use URL as the persistent task identity. `android/app/src/main/java/org/nsa/hall/data/Database.kt:L9-L10` stores task/game/release/manifest/total and no URL/token.
- `services/catalog/app.py:L239-L257` checks visibility, manifest digest, capability owner/expiry and eligibility, then locates the requested object in that manifest and stores its release/manifest/object/bytes/SHA/ETag. `services/catalog/app.py:L293-L295` returns these stored fields. Publication verification actually checks artifact length/SHA bindings and chunk/index/archive identities in `services/worker/main.py:L49-L95` and `services/catalog/packages.py:L20-L75`.
- `android/app/src/main/java/org/nsa/hall/data/Api.kt:L141-L145` sets Range and If-Range. `android/app/src/main/java/org/nsa/hall/transfer/TransferWorker.kt:L130-L135` requires exact Content-Range total and grant ETag, exact body byte count and signed chunk SHA before writing; `TransferWorker.kt:L143-L147` checks accumulated total and whole archive SHA.
- The strong ETag contract is explicit in `docs/engineering/contracts/domain.schema.json:L672-L718`, especially L693-L698; service ETag comes from verified artifact metadata/S3 head or a quoted SHA fallback (`services/catalog/app.py:L255`, L429-L432). ETag is compared as an opaque string by the client, not used as the chunk digest.

**Confirmed source candidate DL-06-D01 — Range requests omit the specified identity encoding constraint**

- Severity: **Medium / P2**, conditional availability/protocol impact; high confidence that the source omission exists. No demonstrated corrupt-file or transparent-decompression vulnerability.
- Required behavior: `docs/engineering/04-transfer-install-save.md:L13,L17` requires requesting `Accept-Encoding: identity` and validating identity on 206.
- Actual behavior: the full `Api.open` body (`Api.kt:L141-L145`) only adds Range/If-Range; `TransferWorker.kt:L129-L135` checks status/range/ETag/body length/SHA but never Content-Encoding. No interceptor supplies the missing identity header in the application client construction (`Api.kt:L52-L75`).
- Concrete unexecuted reproducer: use a controlled object origin that returns the immutable object's ordinary representation when `Accept-Encoding: identity` is present, and chooses an encoded representation otherwise. Resume a task with one good 8 MiB chunk. The next request has Range and If-Range but no explicit identity header; the encoded response is rejected by range/ETag/length/hash checks, producing generic retries and eventually `failed` (`TransferWorker.kt:L42-L47`) even though the origin can serve the required identity representation. Also record a wire assertion that the required header is absent. This needs controlled-origin execution to measure its operational effect; this review did not run it.
- Refutation retained: the pinned declared dependency is OkHttp 4.12.0 (`android/app/build.gradle.kts:L56`). The locally cached 4.12.0 `BridgeInterceptor.intercept` bytecode was inspected with `javap`: offsets 154–184 enable automatic gzip only if both Accept-Encoding and Range are absent; offsets 290–423 transparently decode only when that flag is true. Therefore archive Range requests do **not** automatically gzip/decompress under that dependency. Signed chunk and whole-file hashes also prevent encoded/different bytes from becoming a successful archive. Normal local object serving is identity without extra middleware (`services/catalog/app.py:L603-L621,L477-L492`).
- Scope of remedy for review: explicit identity request/response constraints, with a controlled encoded-response case. Do not describe this as proven corruption, device failure or production-CDN misconfiguration.

**Additional observation, not a corrupt-content finding:** neither new nor renewed grant fields are compared client-side against the persisted manifest, and no ETag is persisted in `TransferRecord` (`HallRepository.kt:L140-L142`; `TransferWorker.kt:L110-L131`; `Database.kt:L9-L10`). This matters if an API violates its own immutable-grant contract. Under the inspected service, create/renew fixes these fields and old chunk/full SHA checks remain independent. A weak or arbitrarily rebound grant requires a faulty/replaced service or external state change not established here. It is not reported as a confirmed mixing defect.

**Paths walked:** UI confirmation `android/app/src/main/java/org/nsa/hall/ui/HallApp.kt:L366` → `enqueue` → `Trust.verify`/`slot` → eligibility/session grant → persisted manifest/task → unique worker → archive session → `Api.open`/HTTPS client → response range/ETag → bounded read → signed chunk SHA → fsync → total/full SHA → install. Error exits at any check reach the bounded worker failure path and do not reach archive append.

**Searched:** `416|Accept-Encoding|Content-Encoding|If-Match` over `android/app/src/main` returned **0 hits**. `etag|ETag|If-Range` over that tree returned **5 lines**: Api.kt L141/L144 and TransferWorker.kt L123/L127/L131; no persistence/schema-validation path was hidden elsewhere. Full Api client, request, send, credential and object-open paths were read.

## DL-06.02 — 只接受匹配 206，禁止 200 追加

> 恢复接受匹配的 206/Content-Range；非零偏移收到 200 不允许追加。
> — `docs/product/产品需求细则.md:L408`

**Verdict:** implemented for this status/range property · confidence: high.

**Where enforcement lives:**

```kotlin
// android/app/src/main/java/org/nsa/hall/transfer/TransferWorker.kt:L130-L135
require(it.code == 206 && it.header("Content-Range") == "bytes $offset-${offset + bytes - 1}/${row.total}")
require(it.header("ETag") == grant.getString("etag"))
val data = it.body!!.byteStream().use { stream -> stream.readBounded(bytes.toInt() + 1) }
require(data.size.toLong() == bytes && sha256(data) == chunk.getString("sha256"))
checkpoint(id)
output.seek(offset); output.write(data); output.fd.sync()
```

Checks precede archive writes, including after the one inline renewal (`TransferWorker.kt:L123-L135`). A 200 at offset zero is also rejected. This is a stricter fallback than accepting a full response, and it satisfies the no-append requirement. `Api.kt:L53` disables HTTP and HTTPS redirects, so an unchecked redirect does not bypass that check. Null/short/oversized bodies throw before write. `Trust.kt:L16-L25` bounds memory/body reads. Content-Encoding remains the D01 limitation, not a second status-range finding.

**Paths walked:** initial range → status/range check; 401/403 → close → API renew → replacement range → same checks; 200/3xx/404/410/412/416/429/5xx → failed `require` → bounded error path, no append; matching 206 → exact bytes/SHA → write; existing valid chunk → no GET → advance verified offset.

**Searched:** all archive object-open call sites are `TransferWorker.kt:L123,L127`; the other transfer `open` is auxiliary full-object indexes at L84, which require 200 and independent signed length/SHA before promotion (L79-L95). No alternate archive 200 fallback or direct response-to-file append was found in the caller/callee sweep.

## DL-06.03 — 416 与错误页

> 416 需核对长度并完整校验，不能直接视为下载成功；错误页不能写进分段文件。
> — `docs/product/产品需求细则.md:L409`

**Verdict:** partial (safe rejection present, named 416 verification branch absent) · confidence: high.

**Where enforcement lives:** the only archive response acceptance is `TransferWorker.kt:L130`, requiring 206. Thus 416 is rejected before body read and before archive write at L132-L135. A 200 HTML error page is rejected on status, and an error body disguised as 206 must still have the exact expected chunk length and signed SHA before writing. After every chunk, and only then, L143-L147 verifies total and entire archive SHA. `Installation.kt:L27-L100` is only reached after that check; normal extraction checks each signed file digest at L49-L65.

**Source gap, not promoted to corrupt-success finding:** no archive 416 branch parses `Content-Range: bytes */N`, compares local length or runs full hash in response to 416; all such responses enter the generic waiting/failed retry handling (`TransferWorker.kt:L42-L47,L129-L147`). This is less than the exact documented response handling. However a valid complete local archive is recognized by rehashing every existing chunk at L113-L119 and issues no Range request, then reaches whole SHA at L147. A conforming same-length immutable object cannot normally return 416 for the missing chunk ranges in the valid signed index. No user-reachable state was established where an otherwise correct complete file receives 416 and is incorrectly accepted or discarded. The safe rejection is evidence against the stronger allegation.

**Concrete unexecuted observation procedure:** retain a correct prefix, inject a 416 for its next missing range, and observe the generic range-mismatch error and retained prefix; local whole SHA is not invoked on that response. This demonstrates the missing specialized branch, **not** an integrity failure or a recoverable-completion bug. No separate severity-bearing defect is asserted without such a consequence.

**Paths walked:** partial/missing chunk → 416 → throw → bounded retry; existing complete archive → per-chunk rehash → no GET → exact total/full hash → installation; auxiliary index 4xx/5xx → fail before partial write; auxiliary 200 wrong content → separate `.partial` file → signed hash fail → not promoted to trusted index (L84-L95).

**Searched:** `416` and `Content-Range` across app/service/tests found the client general 206 comparison, the service's actual 416 generation at `services/catalog/app.py:L607-L610`, and normal-range service assertions at `services/tests/test_distribution.py:L95-L97`; there is no client 416 handler or controlled 416 client test. Entire worker, its entrypoint/error handler, reconciliation and installation completion paths were read.

## DL-06.04 — 同对象续签与正确分段复用

**Verdict:** implemented at the inspected service and task boundaries; external storage deployment not accepted · confidence: high for code.

**Where enforcement lives:**

Changed request identity receives 403 via L545-L546. URL grant HMAC expiry and route/object/method binding are enforced in local delivery at L569-L570 and `services/catalog/crypto.py:L49-L56`; local GET additionally checks verified state and live publication at `app.py:L598-L602`.
- Production signs a GET for the same stored object key (`app.py:L78-L85`; `services/catalog/storage.py:L80-L81`). Bucket/CDN versioning, immutability policy and actual production delivery were not inspected or executed; source-only inspection cannot accept those operational properties.
- `TransferWorker.kt:L124-L127` closes an expired/denied object response, renews the session and retries the same range. Correct chunks are read and rehashed against the trusted chunk index before any network fetch at L113-L119. New worker attempts obtain fresh same-manifest grants at L110 while continuing to reuse correct bytes. Cold-start reconciliation at `StorageReconciliation.kt:L44-L71` validates index identity/digest, rehashes contiguous chunks, trims untrusted tail and persists verified bytes.
- `HallRepository.kt:L144-L157` creates a new UUID task for a selected release; files are isolated by `safeId(task_id)` (`TransferWorker.kt:L103,L109`). Existing task manifest is not rewritten by renewal or transfer actions (`HallRepository.kt:L170-L177`). Cancellation records intent and deletes that task's root on the checked paths at L175 / `TransferWorker.kt:L59-L61`; completion removes its temporary root at L153. This proves path isolation, not complete DL-08 cleanup acceptance.

**Refutations retained:** blindly assigning the returned grant is not enough to establish arbitrary-object mixing: this service cannot return a different stored object on a successful renewal, and the client still hashes each incoming chunk against the original manifest-bound index and the final archive against the original signed SHA. No different-byte archive can become successful merely by changing a grant ETag. No changed-grant corruption finding is asserted.

**Error-handling limit:** the object path renews on **every** 401/403 (L124), not only proven URL expiry. Server local object denials all return bare 403 (L622); a blocked/unlisted release then makes renewal fail (L263). API credential expiry is independently handled by `Api.kt:L104-L109,L77-L93` and service 401 mapping at `app.py:L543-L546`. Non-expiry object denial can therefore incur an unnecessary renewal attempt; authorization bypass was refuted. 404/410 do not trigger policy refresh inside the worker and all protocol errors share the generic five-failure budget (`TransferWorker.kt:L42-L47`). These are supporting protocol observations / DL-09 overlap, not separately counted DL-06 integrity findings.

**Paths walked:** same-object URL 403 expiry → close → authenticated renew → persisted-session identity checks → fresh URL → same range/hash checks; mismatched identity/owner/expired session → 403 → no object write; revoked release → renewal denied → retained task/prefix; worker restart → reconciliation → fresh same-manifest session → verify/reuse existing chunks; user selects another release → new task UUID → separate root. Installation recovery (`Installation.kt:L110-L131`) marks completion only for verified/published journal phases and a matching ready marker/installation checks; it does not convert HTTP 416 into completion.

**Searched:** `download_grant|createDownloadSession|renewDownloadSession|/v1/download-sessions` over service/contracts found two dispatch branches, one shared grant builder, two OpenAPI paths and the service integration tests. `putTransfer|deleteTransfer|TransferWorker|scheduleDownloads|StorageReconciliation|\.open\(` over application main source enumerated all task mutation, scheduling, reconciliation, completion and object-access locations; all DL-06-relevant branches were read.
