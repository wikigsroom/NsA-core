## PKG-06-F01 — 保留，但限定为真实耐久性义务

**作者主张。** VERIFIED 只同步文件及 staging 根，未覆盖嵌套目录/新祖先链接的持久性；在较弱持久性保证的文件系统上，之后掉电可能丢失已发布候选的目录项。

**规范确实强制的属性。**

- `docs/engineering/04-transfer-install-save.md:L59`：VERIFIED 的已完成事实包含“READY及目录落盘”，不是仅文件内容和摘要正确。
- 同章 L64：冷启动按真实目录和 active pointer 对账；“文件/父目录同步失败必须上报，不能用‘已调用rename’宣称耐断电”。
- 产品 L644/L651 对切 active 前“文件完整落盘”与“任意阶段断电”给出跨阶段要求。嵌套资源目录不在条文例外中。

**反证与收窄。** 规格没有规定唯一的系统调用序列，也没有逐字要求“每个目录各调用一次 fsync”。若实现能用经过验证的等效存储保证、可靠的整体同步或可证明的文件系统持久性完成同一义务，也可满足要求；不能只因没看到某个 helper 调用次数就判某手机必定损坏。目录元数据耐久性与 rename 的可见原子性仍是不同义务；“同卷 rename”“文件 fd.sync”“启动时发现损坏”不能自动代替发布前落盘。

**最终保留核心。** 作者指出的缺失屏障若由独立代码审查成立且无等效保证，就属于 PKG-06.02/.03 的强制性源码缺口。Medium/P2 合理，但实际掉电丢目录项取决于目标文件系统/存储保证，仍待故障验证；不是已经实测的数据丢失。修复应证明整个候选及其必要父链接耐久，而不是把某一种 bottom-up 实现方式规定为唯一规范。

## PKG-06-F02 — 保留：不一致候选必须得到受控对账，而不是永久卡住正常恢复

**作者主张。** 单个不一致安装日志被恢复路径反复抛出，初始化不能收敛；保留在磁盘上的旧版/其他有效游戏被全局 ready 门槛阻断。另一独立代码反证另提供“同版本 repair → VERIFIED 后进程退出”的更强可达路径；本规格审查不重做该代码分析，只判断该类修复/边界是否受规范覆盖。

**规范依据。**

- `产品需求细则.md:L652` 要求重启按日志和目录完成或回滚；不是只保存日志、每次遇见同一坏状态继续失败。
- `04-transfer-install-save.md:L60,L64` 允许已发布候选“完成DB登记或保留待恢复”，但缺失/不一致必须记录为 `repair_required` 或恢复中；孤立候选不能自动覆盖有效旧版。
- `docs/engineering/05-data-state.md:L99-L103` 要求核对 READY/active，未知/伪造候选隔离，不执行半包；`产品需求细则.md:L698-L701` 明确快速检查、需修复状态与完整包修复入口。
- S06 `docs/product/页面与交互验收规格.md:L106-L110` 明确失败保留旧版并提供重试/修复。更新页 L386-L389 和 AC-U02 `开发计划与验收矩阵.md:L141` 进一步要求未阻断旧版在更新失败后仍可使用。
- AC-P05 和 CON-06 包含验证/发布/DB 边界重启及关键文件丢失，支持对这类恢复不一致的测试范围。它们不只覆盖最常见的首次安装成功路径。

**有效反证边界。** “新版本待恢复”允许暂时保留未完成操作；首次扫描期间保守阻止启动也符合 ADR 0007（`docs/engineering/decisions/0007-policy-runtime-save-recovery.md:L49`）。规范没有要求跳过必要核验立即启动、不要求对损坏或兼容性不明的唯一旧版强制自动回退，也不要求启动时重新全量 hash 资源（05-data-state.md L101）。因此，单次抛出并进入有实际修复/回滚动作的维护流程本身不构成此缺陷。

**保留的违例条件。** 独立代码审查若确认同一候选使恢复永久不收敛、既没有受控完成/回滚/修复动作，也使本可用且未阻断版本长期不可访问，则“磁盘上还留着旧文件”不是替代满足路径。可以用逐候选隔离、持久待恢复记录/用户修复、验证后恢复旧引用等方式满足要求，规格不强制某一种异常捕获结构。High/P1 以已经保留的全局库阻断代码影响为条件；本反证仅确认其规范适用性，没有执行故障。

## PKG-06-F03 — 保留，但清理允许延后，义务不得遗失

**作者主张。** 正常安装先记录 CLEANED/删除日志，worker 后清下载；恢复路径可直接将 transfer 完成并删日志，使归档/索引临时目录再无清理执行者。结果是大包长期残留。

**强制规范。**

- `产品需求细则.md:L650` 把“清理”列入持久提交日志；L652 要求重启对账完成或回滚。
- `04-transfer-install-save.md:L61` 明文允许 DB_ACTIVATED 后“允许启动，清理延后”；**L62 的 CLEANED 才表示“无引用下载/临时已清”，幂等结束。**
- 同章 L66 要分别核对 active/pending/session/rollback/唯一备份引用；L86 要求删除失败记录待清理及真实残留字节。`05-data-state.md:L117-L119` 要求分类计量、所有权/引用复查及清理完成记录；删 DB 行不等于物理字节清除。

**收窄与替代满足路径。** 单看激活成功时归档尚在并不违反规范；短暂保留用于受控恢复也允许。独立清理 worker、可重建的持久清理队列或另一份可靠所有权记录都可在移除安装日志后接手，不强制在 installer 内同步递归删除。真正被否定的是把实际未清且无合法引用的临时归档宣称 CLEANED，然后丢失所有可重放的清理责任。若另有有效引用或完整的后续清理机制，应撤销或缩小对应文件的残留结论；文件是否仍被引用、是否有替代执行者由独立代码反证判断。

**最终保留核心。** 无引用下载/临时清理必须最终能够幂等完成，故作者提出的“终态后永久丢失清理义务”属于 PKG-06.01/.03。Medium/P2 与多 GiB 累积影响相称，但具体残留量、清理中断窗口及实际磁盘影响仍待执行验证。不能把没有立即清理扩大为所有成功安装都不合规。

## PKG-06.04 与邻接范围的反证

“仅保留所有旧版本、不自动回收”满足“条件成立前不得提前删”的限制；规格没有强制必须在健康后自动 GC。因而不能把作者描述的保守保留改报为早删旧版。健康/回退功能不完整属于相应 UPD 需求，不能不加区分地计入本次三个 PKG-06 候选。显式用户删资源也不等同自动更新 GC。

规范同样允许短提交临界区不立即取消（04 L66）；不用“任何时候都必须瞬间取消”的额外要求来扩张本次报告。未发现允许跳过耐久、坏候选对账或 CLEANED 真实语义的 P1/首版豁免。
